# Skills: comparative research

**Roadmap item 12.** Local source inspection on 2026-09-28. Status means a usable skill flow in the inspected checkout, not feature parity with Dive. Paths below are relative to each named checkout; revisions pin the evidence. No live runtime test was performed.

## Dashi baseline and consumer

Dashi has a definition, not an implementation: a skill is “named task instructions loaded into context when invoked” (`design/ubiquitous-language.md:27`). The roadmap says there is no Dive-equivalent loader and asks for a real consumer before adding one (`design/remaining-work.md:116-123`). Today a host can put a short catalog in `Agent.Instructions`, bind a `tool.Toolset`, and return instructions through a local tool (`turn.go:23-45`, `runner.go:21-38`, `tool/tool.go:455-479`). Dashi records tool results and supplied context for recovery (`turn.go:116-128`); only `ContextOperator` may carry system/developer authority (`context_origin.go:5-30`). Agent auto-revision cannot see tools, so a host changing a skill bundle must version it explicitly (`turn.go:27-31`).

**Consumer check:** Mobius Cloud has a live, application-owned assigned-skill flow, but still imports Dive (`internal/agentruntime/executors/agent_skills.go:8-9,32-63`). It is a credible migration consumer for catalog/load mechanics, not evidence that Dashi needs skill storage, permissions, or marketplace machinery. Nvoken's agent request has instructions, tools, and MCP servers but no skill field (`internal/adapters/httpapi/target_agents.go:15-28`); no first-party runtime skill flow was established in the inspected `internal/` tree.

## Lessons for Dashi

1. **Progressive disclosure is the common useful primitive.** A short catalog and an explicit load operation give the model enough to choose without front-loading every body. Mobius, ADK, MAF, and OpenHands use a named load tool; pi uses its existing file reader. A Dashi package should expose a clear, ordinary tool result so the turn records exactly what was loaded.
2. **Selection and authority belong to the host.** Mobius filters assignments and enforces action constraints in application code. OpenHands and pi distinguish model-invocable from user-invocable skills. Skill text, especially project or marketplace content, must not silently become operator instructions or grant tools. Dashi's `ContextOrigin` gives the needed boundary.
3. **Keep execution separate.** Dive's optional shell expansion, OpenHands' inline shell, and MAF's script tool show why “load instructions” and “run code” must be different capabilities. Dashi's first skill slice need not execute scripts, fetch remote sources, or auto-register MCP servers.
4. **Avoid drifting catalogs.** Dynamic request-time injection is easy to wire, but Dashi's recovery requires stable, recorded behavior. Build a per-turn snapshot from the host-approved skill set; include its digest in `Agent.Revision` or another explicit revision when it changes. Duplicate names and missing bodies should fail clearly at construction or load.

**Evidence limits:** This is a source review of pinned local checkouts, not a claim that all documented behavior is exercised by current production users. Nvoken's working tree includes unrelated changes; cited Nvoken files were clean relative to `deea133a`. No external web source was needed for these code-grounded comparisons.
