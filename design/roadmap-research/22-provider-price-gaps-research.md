# 22. Remaining provider price gaps: comparative research

**Status:** Draft research, 2026-09-28. **Scope:** List-price evidence, observable billable units, and the developer path for qualifying an estimate. The implementation candidate is the provider example's served-model check; this packet does not claim a newly qualified provider rate. Local source citations are pinned to the commits below; provider pages were checked on 2026-09-28.

## Dashi baseline

Dashi's catalog is exact-model, API, and endpoint scoped; `Entry.Bind` carries a source and qualified date (`design/model-catalog.md:23-50,92-106`). A `Pricing` sheet names its currency, date, source, four token rates, tiers, modality rates, and per-*request* hosted meters (`llm/pricing.go:121-142`). `Pricing.Estimate` requires sufficient token detail. A missing hosted meter price produces a known lower bound plus `Cost.UnpricedRequests`, never a free call (`llm/pricing.go:228-295,375-385`). A partial cost is not valid proof under a hard budget (`design/hosted-tool-pricing.md:83-97`).

`Pricing.Estimate` is deliberately a calculation over a **previously qualified** sheet; it cannot check a provider response's identity by itself (`llm/pricing.go:228-242`). `Entry.Serves` accepts only the exact model ID or its documented snapshot (`catalog/catalog.go:108-114`). The model-call guide tells callers to use that check before estimating (`docs/guides/model-calls.md:192-201`). Yet the runnable provider example fetches `client.ModelInfo(requestedModel)` and estimates `result.Usage` without inspecting `result.Served` (`examples/providers/main.go:139-163`). It also renders a non-nil `result.Cost` as a plain amount without testing `Partial()`. A provider-reported cost can stand independently of the catalog; a list-price estimate cannot. This is a verified developer-facing qualification gap even if no new price can be added.

The OpenAI Responses adapter counts `image_generation_call` as one `image_generation` request (`providers/openai/responses/meter.go:12-23,64-91`) but decodes only `tool_usage.web_search.num_requests`; it does not put `tool_usage.image_gen`'s token breakdown into `Usage` (`meter.go:117-139`; `responses.go:649-670`). Existing captured web-search fixtures contain **zero** image-gen token fields, not a positive image-generation example (`providers/openai/responses/testdata/openai-web-search.json:150-159`). `ImageGenerationToolOptions.Model` independently selects a GPT Image model; `Result.Served` identifies the mainline Responses model (`providers/openai/responses/hosted_tools.go:65-92`; `responses.go:649-660`). Mainline `Usage.ModalityTokens` is not a second model's meter (`llm/usage.go:12-27,30-75`). Therefore copying image-model rates onto the mainline catalog sheet, or treating one call as one image, would misprice the tool. The catalog explicitly lists this route as unpriced (`catalog/sources_test.go:1255-1259`).

Other explicit gaps are Anthropic code-execution container hours and MCP, OpenAI code-interpreter sessions and a fixed search-token block on `gpt-4.1-mini`, and xAI image generation with model-dependent per-image rates (`catalog/sources_test.go:1235-1274`). Meta's query count assumption is marked unverified even though a rate is recorded (`sources_test.go:1220-1231`). Dashi intentionally leaves speed/service-tier variants and media prices outside this catalog (`design/model-catalog.md:111-152`). The coverage test inventories every emitted hosted meter and requires either a price or an unpriced reason (`design/hosted-tool-pricing.md:60-66`; `catalog/sources_test.go:1277-1310`).

## Official provider check and lessons

The [OpenAI image-generation tool guide](https://developers.openai.com/api/docs/guides/tools-image-generation) confirms a separately selected GPT Image model inside a Responses call. The [image-generation guide](https://developers.openai.com/api/docs/guides/image-generation) states mainline token charges are additional, lists distinct image/text and cached token rates for GPT Image 2.5, and warns that cached image-tool input is billed but its cached token count is **not included** in Responses output. It also charges additional image output tokens for streamed partial images. The [model page](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst) verifies a concrete model rate, but a published rate alone does not prove the tool's served model or complete billable usage. No rate is proposed from an unobserved unit.

Dive's direct-image split and pi's separate image catalog suggest modeling the tool's model and usage independently when a provider actually reports enough detail. Nvoken and Mobius show the application demand for a usable cost signal, while their fallbacks demonstrate why Dashi must label approximation and partial coverage. Dashi's source rows, exact endpoint binding, and partial-cost semantics are the stronger starting point. The narrow code opportunity today is to make the public example follow the catalog's existing qualification contract and demonstrate unknown and lower-bound output. This changes developer behavior without adding an unsupported rate or a new public API. The route-by-route evidence workflow remains the path for later price additions.

**Evidence limits:** Status means verified behavior in the cited paths, not a repository-wide absence claim. Nvoken's cited `generator.go` lines were checked with `git show HEAD`; its working tree has unrelated changes. Dashi baseline: `f6098c0` (`origin/main`, 2026-09-28). The OpenAI [image-generation guide](https://developers.openai.com/api/docs/guides/image-generation) was rechecked on 2026-09-28: it says billed cached image-tool input counts are omitted from Responses output and partial images add output tokens. Meta's source row itself labels its query-count mapping unverified (`catalog/sources_test.go:1220-1231`); no invoice comparison was available, so it is not a candidate for a new completeness claim.
