# 07 — Authenticated provider-hosted MCP: research

**Status:** research snapshot, 2026-09-28. **Question:** how can an application let a model provider connect to a private MCP server without putting its credential in Dashi's durable record? A provider-hosted connector sends the credential *to the model provider* in the model request. A local MCP client instead connects from the application; its authentication and approval boundaries differ.

## Dashi baseline

Provider-hosted MCP is available only without authentication. OpenAI Responses `NewMCPTool` accepts a server label, HTTPS URL, allowed tools and approval policy; its default is ask every time. Anthropic Messages `NewMCPTool` accepts a name and HTTPS URL. Both reject embedded URL credentials and query strings. An injected `authorization` option fails at `Prepare` rather than slipping into the wire request (`providers/openai/responses/hosted_tools.go:95-117,246-289`; `hosted_test.go:249-275`; `providers/anthropic/messages/hosted_tools.go:142-165,269-297`).

`llm.RequestSnapshot.Body` and `Request.Body()` currently contain the **same exact provider payload**, and Runner records `req.Snapshot()` (`llm/request.go:12-35,61-66,131-165`; `runner.go:1095`). Putting a token in today's hosted options or encoded body would therefore expose it through recordable intent. Dashi already models OpenAI hosted approval as explicit content: Runner stops waiting, then the application settles the specific pending request (`runner.go:519-531,1340-1379`; `llm/hosted.go:99-152`). The [hosted-tool plan](../2026-09-27-resources-and-hosted-tools.md) requires private exact dispatch bytes, a redacted verifiable snapshot, named secret bindings and no token in `Input`, snapshot, `Raw` or errors (lines 66-73). [Roadmap item 7](../remaining-work.md) is disabled pending that split (lines 75-81).

## Lessons and tradeoffs

1. **Keep connection identity and secret value separate.** Nvoken shows a stable, recordable binding reference with turn scope; Dive and Agent Framework show why embedding tokens in a public hosted tool object is convenient but problematic when that object is recorded. The resolver should check provider, server URL, binding and application scope at preparation time, then fail closed on expiry or revocation.
2. **The application should own OAuth.** OpenAI's [remote MCP API](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) and Anthropic's [MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector) accept access tokens in the provider request. Both assign OAuth to the API consumer; OpenAI says its Responses API does not store the supplied `authorization` value, so it must be supplied on each creation request. Mobius/OpenHands show how much state a complete OAuth UX adds. Dashi can accept an app-resolved token first, without becoming an OAuth server or vault.
3. **Connection access and tool approval are separate.** An authorized credential permits the provider to contact a server; it does not mean every tool call is approved. Dashi's existing OpenAI approval content can keep the application in the loop. Anthropic's surveyed Dashi adapter rejects hosted approval responses (`providers/anthropic/messages/messages.go:582-589`); a common “approval” switch would mislead users.
4. **Protect every observable copy.** A redacted record is insufficient if `Request.Body()`, provider error text, streamed `Raw`, traces or callback parameters still expose the token. Secret-bearing prepared requests must be clearly non-recordable and non-exportable; recovery must resolve a fresh token and create a new dispatch attempt, especially after uncertain delivery.
