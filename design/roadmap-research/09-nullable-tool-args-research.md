# Nullable typed-tool arguments: source review

**Status:** Research refreshed against Dashi `f6098c0`, 2026-09-28. **Roadmap:** [item 9](../remaining-work.md), size S / low difficulty. Paths below are relative to the named checkout; revisions pin the source. This compares **schema emitted**, **local validation**, and **decoded callback value**. Provider acceptance is a separate question.

## Dashi baseline

`tool.Func[T]` generates a schema once with `wonton/schema.Generate`, publishes it in `tool.Definition`, compiles those same bytes as JSON Schema draft 2020-12, then validates each call **before** `encoding/json` decodes into `T` (`tool/function.go:21-79,95-124,208-223`). `wonton` v0.2.1 marks a pointer field with `"nullable":true` while retaining a single `"type":"string"`/`"object"`/etc. (`schema/generate.go:149-163` in the pinned module). Draft 2020-12 validation ignores the `nullable` extension: `{"value":null}` fails against `type` even though Go would decode it to a nil pointer. `wonton` also lets a field's `nullable` tag override the pointer-derived value; malformed tag values are silently ignored (`schema/generate.go:310-324`). A `nullable:"true"` tag on a non-nilable scalar could otherwise advertise a null that Go decodes as a zero value.

`omitempty` and `required` govern **presence**, not whether a present value may be null (`wonton/schema/generate.go:277-300,409-420`). A required `*string` should accept present null and refuse omission; an optional `*string` should accept both. Root `*Args` is a separate case: `wonton` emits an object schema at the root (`schema/generate.go:60-79`), so root `null` should remain invalid. Current `tool/tool_test.go:17-58` covers general argument rejection, while `:383-385` checks only that a pointer root can be constructed. `go test ./tool` passes at `f6098c0`, but there is no pointer-property null test. [Example-port follow-ups](../gaps/F-example-ports.md) record the mismatch.

Reviewer follow-up: Wonton emits **no base `type`** for `any` and `json.RawMessage` (`schema/generate.go:97-100,165-167`), including `*any`/`*json.RawMessage` after pointer reflection. Such a schema already accepts null, so a conversion must not invent a type union. Conversely, `nullable:"false"` cannot prohibit null in an unconstrained schema without a different JSON Schema expression; silently stripping that tag would misstate the developer's intent. For this focused item, explicit `nullable:"true"` on non-pointer fields is rejected even when a slice or map could decode null; broader nilable types need their own agreement tests.

## Lessons and provider boundary

The user-facing distinction is **omitted**, **present null**, and **present value**. A Go `*T` callback receives nil for either omitted or null; `Call.Args` retains the original JSON if an application must distinguish them (`tool/function.go:115-124`). A nullable enum needs `null` in its `enum` as well as its `type` union, because both constraints apply. Pi's separate strict-provider schema is useful, but Dashi should first fix its **single local contract**: generated schema, validation and decode must agree. Avoid a broad, silent null-to-omission rewrite.

[JSON Schema's object guide](https://json-schema.org/understanding-json-schema/reference/object) explicitly distinguishes absent from null. Dashi's OpenAI Responses adapter passes local `Definition.Schema` through with `strict:false` (`providers/openai/responses/responses.go:236-252`); Anthropic Messages and Gemini likewise forward the schema (`providers/anthropic/messages/messages.go:260-273`; `providers/google/gemini/gemini.go:327-343`). [OpenAI's current Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) supports null unions in **strict** mode but also requires every field to be `required` and `additionalProperties:false`. Thus a correct Dashi schema does **not** establish that every provider route accepts it, nor does it make an `omitempty` field OpenAI-strict-compatible. Provider request shaping and live acceptance belong to conformance/qualification ([items 4–5](../remaining-work.md)). No live provider call was made.
