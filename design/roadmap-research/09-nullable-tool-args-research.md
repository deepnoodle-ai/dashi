# Nullable typed-tool arguments: source review

**Status:** Research snapshot, 2026-09-28. **Roadmap:** [item 9](../remaining-work.md), size S / low difficulty. Paths below are relative to the named checkout; revisions pin the source. This compares **schema emitted**, **local validation**, and **decoded callback value**. Provider acceptance is a separate question.

## Dashi baseline

At `015b0ec`, `tool.Func[T]` generates a schema once with `wonton/schema.Generate`, marshals those bytes into `tool.Definition`, compiles them as JSON Schema draft 2020-12, then validates each call **before** `encoding/json` decodes into `T` (`tool/function.go:22-113, 188-215`). `wonton` v0.2.1 marks a pointer field with `"nullable":true` while retaining a single `"type":"string"`/`"object"`/etc. (`schema/generate.go:149-163` in the pinned module). The draft 2020-12 validator does not treat `nullable` as an instruction, so `{"value":null}` fails against that `type` even though Go could decode it to a nil pointer. The existing `tool/tool_test.go:14-58` covers invalid arguments but not a pointer-valued property; `:383-385` only checks a pointer **root type** can be constructed. [Example-port follow-ups](../gaps/F-example-ports.md) record the mismatch. `omitempty` controls whether a property is required; it does **not** itself permit explicit null. A required `*string` should accept a present null, while an omitted required key must still fail.

## Lessons and provider boundary

The user-facing distinction is **omitted**, **present null**, and **present value**. A Go `*T` callback receives nil for either omitted or null; `Call.Args` retains the original JSON if an application must distinguish them. `omitempty` governs requiredness, while pointer/nullable governs allowed values. Pi's separate strict-provider schema is useful, but Dashi should first fix its **single local contract**: generated schema, validation and decode must agree. Avoid a broad, silent null-to-omission rewrite.

[JSON Schema's object guide](https://json-schema.org/understanding-json-schema/reference/object) explicitly distinguishes absent from null. [OpenAI's current Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) supports null unions for optional semantics in strict mode but also requires every field to be `required` and `additionalProperties:false`. Thus a correct draft 2020-12 Dashi schema does **not** establish that every Dashi provider route accepts it, nor does it make an `omitempty` field OpenAI-strict-compatible. Provider request shaping and live acceptance belong to the provider conformance/qualification work ([items 4–5](../remaining-work.md)). No live provider call was made for this review.
