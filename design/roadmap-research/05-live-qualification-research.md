# Live provider qualification — research

Status: source survey, 2026-09-28. Roadmap [item 5](../remaining-work.md). This reviews how projects **prove** provider behavior and communicate the proof to developers. “Live” means a request reached a real remote model; local server tests and recorded HTTP cassettes are fixture evidence. No paid probes were run for this survey. The comparison notes in `tmp/research/comparison/` were orientation; locations below were checked in source.

## Dashi baseline

The [live test guide](../../docs/dev/live-tests.md) separates ordinary `go test -race`, `go vet`, and `go build` from opt-in paid tests. `internal/providertest/live_agent.go:18-50,321-333` supplies shared Runner checks; `providers/live_agent_test.go:16-21` and the separate Gemini module's `providers/google/gemini/live_contract_test.go:34-35` invoke them. Opt-in flags and provider keys guard spending. The guide records dated passes for Anthropic Messages, OpenAI Responses, and Gemini API on selected models, plus feature-specific image, tool, structured-output, and error probes. `providers/error_reasons_test.go:101` ties recorded rejection fixtures to live observations. Important gaps: proof is spread through prose and tests; a reader cannot scan one route/model/feature table to distinguish fixture-only support, a dated live pass, a failure, and an unrun case. The guide explicitly says Gemini errors remain unrun without a key and other routes are not qualified.

## Lessons and evidence boundary

1. **Use a narrow proof claim.** Nvoken's public sweep and OpenHands' task suite prove different things. Dashi should state exact provider, API route, model, feature, stream mode, date, and test—not just “provider supported.” An alias may serve a different model later.
2. **Keep fixture, replay, and live separate.** Pi's dialect corpus and ADK's cassettes are valuable; neither means the current remote endpoint accepted today's request. Local Go tests must remain credential-free and deterministic.
3. **Show skipped work.** Credential-gated `t.Skip`/`skipIf` is good cost control but easy to misread as a pass. Dashi's run instructions and result record should show `not_run`, `skipped`, `passed`, or `failed` per selected row. No key must never promote a claim.
4. **Make targeted probes easy and bounded.** Existing Dashi tests already name paid-call counts and allow `-run` filtering. Nvoken's one-provider selection and JSON result are a good usability model. Keep the first Dashi version as a small documented matrix and targeted commands, not a new test platform.
