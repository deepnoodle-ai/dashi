# Speech transport — research

Status: source and provider-document survey, 2026-09-28. Roadmap [item 8](../remaining-work.md). This distinguishes **audio content** in an LLM message, a **batch speech endpoint** for recognition or synthesis, a **speech stream** with incremental audio/text, and a **live voice session** with two-way turn-taking. The projects do not offer the same capability just because each represents audio. `tmp/research/comparison/` provided orientation; the locations below were checked in source. No live speech calls were made.

## Dashi baseline

`speech/speech.go` defines validated `TranscribeInput`, `SynthesizeInput`, `Transcription`, and `Synthesis`, but no client or transport. Recognition can legitimately return empty text for silence; synthesis yields a `content.Block`, not a playback or durable-storage claim. `speech/capabilities.go` keeps batch, audio streaming, and incremental text support separate and scopes claims through `ModelInfo`. `content/content.go` carries audio bytes, URLs, provider IDs/URIs, origin, and frame format without fetching them. `content/mime.go` does not have an audio extension table, so preparation must verify accepted upload MIME explicitly. The [media and speech proposal](../media-and-speech-proposal.md) proposes Prepare → Send batch calls, distinct speech streams, and a separate realtime package. `media/request.go` and `providers/openai/images/` establish explicit destination binding and prepared multipart payloads, though their public snapshots include binary bodies and would be expensive or unsafe to copy into speech logs.

## Lessons and tradeoffs

1. **Make the operation explicit.** Dive's dedicated endpoint calls give callers a direct file → transcript or text → audio flow. Eino/MAF audio blocks support a different job: letting an LLM reason over media. A Dashi `Recognizer` and `Synthesizer` should return typed speech results rather than repurposing an `llm.Message` response.
2. **Prepare exact behavior before dispatch.** OpenAI multipart ASR and Gemini's dedicated Files API + Interactions route differ materially. Model/API routing, accepted source type, audio MIME, language, timing, voice, format, and any fallback must be visible or rejected before remote work. Unsupported options cannot quietly disappear. The requested model should survive in the result; served model stays unknown unless a response actually reports it.
3. **Treat silence and transport failures correctly.** An empty provider transcript can mean no detected speech; it should not automatically be `ErrNoResult`. Uploaded bytes, response size, cancellation, and uncertain dispatch need bounded/observable handling. Generated audio is data; the application owns storage and playback.
4. **Keep streams distinct from live voice.** A one-way stream can yield partial/final transcripts or audio chunks without a conversation runtime. ADK's Gemini Live path includes bidirectional turn-taking and reconnection concerns; folding it into simple speech calls would burden the common batch UX. Specify ordering, finalization, and cancellation against at least two provider shapes before committing public stream interfaces.

## Current provider routes and first-slice choice

- [OpenAI file transcription](https://developers.openai.com/api/docs/guides/speech-to-text) sends a completed file to `/v1/audio/transcriptions`; the guide sets a **25 MB** file limit. The [API reference](https://developers.openai.com/api/reference/cli/resources/audio/subresources/transcriptions/methods/create) documents multipart `file` + `model` and a JSON result with `text`; `gpt-4o-mini-transcribe` supports the plain JSON route, language, and prompt. Word/segment timestamps and speaker labels require other response shapes or models, so an initial adapter must reject those hints. It must not infer recognized language from the requested hint.
- [OpenAI speech creation](https://developers.openai.com/api/reference/cli/resources/audio/subresources/speech/methods/create) sends JSON `input`, `model`, `voice`, optional `instructions`/`speed`/`response_format` to `/v1/audio/speech`, returning audio bytes. `gpt-4o-mini-tts` is a documented model; speed is 0.25–4.0 and input is limited to 4096 characters. The route has no language setting. The first adapter can select MP3 only, with a bounded response read; it cannot claim a served model or response ID absent from the wire.
- [Gemini 3.5 Transcribe](https://ai.google.dev/gemini-api/docs/transcribe) is now a **dedicated** recognition model. The documented Go path first uploads to the Files API, then passes its URI to Interactions; it supports language hints, timestamps, and diarization with route-specific constraints. This corrects the earlier impression that Google's only option is prompted general audio understanding. The upload/interaction pair has separate remote outcomes and file lifetime; hiding both inside one `SendTranscription` would undermine prepared-call clarity. [Gemini TTS](https://ai.google.dev/gemini-api/docs/speech-generation) is another distinct output shape. Research these as follow-on adapters after the single-attempt OpenAI batch path is settled.

The first slice should cover **both** batch operations at one explicit OpenAI destination. This is smaller and more usable than one operation each from two providers. It proves the common `speech` vocabulary but does **not** qualify cross-provider parity. Fixture tests prove local encoding/decoding; only named, opt-in live probes can establish provider acceptance and model behavior.
