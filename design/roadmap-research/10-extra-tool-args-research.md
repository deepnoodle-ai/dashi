# Tolerance of extra tool arguments — research

Status: source survey, 2026-09-28. Roadmap [item 10](../remaining-work.md). This follows three separate decisions: what the model-facing schema advertises (`additionalProperties`), what the runtime validates, and what the typed callback actually receives. `tmp/research/comparison/` supplied orientation; locations below were checked in source. No live provider call was made.

## Dashi baseline

`tool/function.go:19-79` generates one JSON Schema for `tool.Func[T]` with `DisallowAdditionalProperties: true`, then compiles it. `:92-124` validates the original JSON against that schema and decodes with `DisallowUnknownFields`, so an extra key fails twice in principle. `tool/tool_test.go:16-48` explicitly expects `{"query":"yes","extra":1}` to return `StateNotExecuted` with no callback. The [tools guide](../../docs/guides/tools.md) documents nested objects as closed. The runner independently calls `validateToolCall` before policy or execution (`tools_loop.go:153-184`, `tool_args.go:13-40`); it records `not_executed`/`invalid arguments` and sends `Invalid tool arguments: …` to the model. A retry needs another model call and can exhaust the default eight settled attempts (`turn.go:78-109`, `runner.go:902-907`). The raw `Call.Args` remains the recorded call, and policy can rewrite it, so any tolerance must keep the validated typed input and recorded raw JSON understandable together. Provider preparation preserves caller schemas (`providers/providers_test.go:168-200`); OpenAI Responses explicitly uses `strict:false` (`providers/openai/responses/responses.go:236-254`). No Dashi provider fixture in the inspected tests establishes a live frequency of extra keys; the current rejection is proved by the local unit test.

## Lessons and tradeoffs

1. **Extra is not malformed.** An unknown key beside valid required values can be safely ignored by a typed struct callback; missing required values, wrong types, invalid enum/range, malformed JSON, and schema-declared map entries still require validation. Dive and Pi illustrate the common usability advantage; Eino illustrates how advertised and runtime rules can drift.
2. **Keep raw and effective views clear.** Dashi already records the original JSON and exposes it to policy. The typed `T` can ignore unknown keys, but developers must know that `Call.Args` still contains them for audit/authorization. Do not silently rewrite the raw record or treat unknown data as a typed argument.
3. **Let strict tools opt in.** Some tools use a closed object as an intentional contract, and Microsoft/OpenHands show a defensible strict choice. Changing Dashi's `tool.Func` default is a compatibility change; an explicit per-tool strict option can retain the old behavior without burdening the everyday case.
4. **Do not claim provider proof from local acceptance.** Dashi's provider adapters preserve schemas and OpenAI Responses uses non-strict mode, but current fixtures do not show how often real models emit extra keys. Add a recorded provider example when observed; label it fixture evidence and qualify live behavior separately.
