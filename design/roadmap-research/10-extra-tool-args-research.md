# Tolerance of extra tool arguments — research

Status: source survey refreshed against Dashi `16700d1` on 2026-09-28. Roadmap [item 10](../remaining-work.md). The relevant boundaries are what the model-facing schema permits (`additionalProperties`), what the runner validates before authorization, and what the typed callback decodes. The git-ignored `tmp/research/comparison/` supplied orientation; locations below were checked in source. No live provider call was made.

## Dashi baseline

`tool/function.go:34-81` generates one JSON Schema for `tool.Func[T]` with `DisallowAdditionalProperties: true`, then compiles it. `:100-133` validates against that schema and decodes with `DisallowUnknownFields`; either check refuses an extra key. `tool/tool_test.go:17-48` expects `{"query":"yes","extra":1}` to return `StateNotExecuted` without calling the callback. The [tools guide](../../docs/guides/tools.md) says nested structs are closed. The runner separately validates the call before `BeforeTool` hooks or execution (`tools_loop.go:172-197`, `tool_args.go:13-38`), records `not_executed` / `invalid arguments`, and asks the model to correct it. A retry spends another model attempt; the default limit is eight (`turn.go:78-109`). The runner and executor must accept the same bytes or a hook could authorize a call that still cannot run.

`wonton/schema.GenerateOptions.DisallowAdditionalProperties` controls root and nested struct schemas (`schema/generate.go:55-78,240-258` in v0.2.1); without it, those schemas omit `additionalProperties`. [JSON Schema permits extra keys by default](https://json-schema.org/understanding-json-schema/reference/object). Wonton still emits a value schema for declared map fields (`schema/generate_test.go:451-468`), so opening *structs* need not turn maps into unvalidated bags. This should be checked with Dashi's nullable pointer normalization, introduced by item #9.

`Call.Args` is the effective JSON and is recorded; when a `BeforeTool` hook rewrites it, the model's original bytes move to `Call.RequestedArgs` (`hooks_run.go:397-417`, `tool/tool.go:185-205`). Hooks inspect the raw effective JSON, not a pruned struct. Go's ordinary struct decoding ignores unknown sibling keys, but `any`, `json.RawMessage`, and custom `UnmarshalJSON` types may still receive dynamic content. Tolerance is **not input sanitization**. Provider preparation preserves supplied schemas (`providers/providers_test.go:168-200`); OpenAI Responses explicitly sends `strict:false` (`providers/openai/responses/responses.go:236-254`). No inspected Dashi fixture measures how often a live provider emits extras.

The four local provider routes expose the same definition in different wire locations: Responses `tools[].parameters` with `strict:false` (`providers/openai/responses/responses.go:236-255`), Chat Completions `tools[].function.parameters` (`providers/openai/completions/completions.go:220-244`), Anthropic `tools[].input_schema` (`providers/anthropic/messages/messages.go:262-279`), and Gemini `tools[].functionDeclarations[].parametersJsonSchema` (`providers/google/gemini/gemini.go:328-348`). The cross-provider schema-preservation test (`providers/providers_test.go:172-200`) currently covers Responses and Anthropic through its `cases` table, not Chat Completions or Gemini. These are offline serialization facts, not promises that a provider samples only declared keys or accepts every open schema.

The only in-library `tool.Func` call site outside tests is the read-only `skill` loader (`skill/skill.go:176-190`); other non-test calls are examples and live qualification helpers. Side-effecting examples include `deploy` under immediate or durable approval (`examples/approval/main.go:35-61`, `examples/durable_approval/main.go:36-60`) and detached `send_email` (`examples/resume/main.go:89-104`). Their callbacks use declared fields, but opening schemas silently would teach a changed exact-key contract in examples of external effects. An implementation migration audit should make a deliberate strict/default choice at each site. This is a scoped code finding, not proof that downstream applications do not depend on the current default.

## Lessons and tradeoffs

1. **Validate declared meaning.** An unknown key beside valid required values can be ignored by an ordinary typed struct callback; missing required values, wrong types, invalid enum/range, malformed JSON, and declared map entries still need validation. Dive and Pi show the usability benefit; Eino shows how advertised and runtime rules can drift.
2. **Keep the raw/effective distinction.** Do not silently prune `Call.Args` or treat unknown keys as validated callback inputs. When a hook rewrites, `RequestedArgs` preserves the model's bytes. `Call.Args` is not a sanitized object, and custom decoders can have their own behavior.
3. **Permit deliberate strictness.** Microsoft and OpenHands show a valid closed-contract choice. Opening `tool.Func` by default changes behavior, including for misspelled *optional* fields that would now be ignored. A per-tool strict option preserves rejection without a global switch. Pi's tool-specific split is a reminder that local tool semantics may require strictness even when the provider's sampling is permissive.
4. **Qualify providers honestly.** A local unit test and transmitted schema fixture can prove Dashi's contract, not live provider frequency or acceptance. Record live route/model evidence separately when available.
