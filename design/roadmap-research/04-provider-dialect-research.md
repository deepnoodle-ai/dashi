This item concerns deterministic wire parsing, request preparation, and cross-provider replay tests. Paid live qualification is [item 5](../remaining-work.md).

## Dashi baseline

Dashi already has a useful start. `internal/providertest/providertest.go:1-6, 102-180` shares contract checks across the root and Gemini modules. `providers/providers_test.go:28-63, 68-132` runs equivalent blocking and streaming fixtures, including private replay and incomplete responses, but its `cases` table currently names Anthropic and OpenAI Responses (`:717-790`). `providers/content_replay_test.go:21-60` tests each source/target pair from that table, with a single portable history shape and both transports. Gemini has its own shared final-facts check in `providers/google/gemini/contract_test.go:79-101`. Chat Completions has focused chunk tests (`providers/openai/completions/completions_test.go:99-145, 320-344`) and a stream assembler keyed by tool index (`stream.go:20-53, 199-224`). Some fixture bodies were captured from providers; many are hand-written. `docs/dev/live-tests.md:7-16` correctly labels ordinary tests as local fixture tests.

The gap is **coverage and evidence**, not a missing testing framework. The current pair matrix does not exercise the separate Gemini module, Chat Completions wrappers, multiple concurrent tools, missing/reused indices or IDs, empty arguments, and changing stream chunk order. A one-case final-facts check does not establish dialect conformance for those cases. Dashi's `llm.ModelInfo` already scopes capability claims to a model/API/endpoint and evidence method (`llm/model.go:174-192`); it has no general dialect-trait bag. Chat Completions `Config` has a few explicit route settings (`providers/openai/completions/completions.go:22-50`).

The pre-change Chat Completions stream assembler (`providers/openai/completions/stream.go:25-29, 206-241` at `018af907`) groups fragments by an `int` index. Its wire type (`wire.go:309-314`) cannot distinguish an omitted index from index zero. A reused index can overwrite ID or name while retaining earlier arguments, and two indices can finish with the same ID; `tool.Call.Validate` checks each call's shape but not uniqueness (`tool/tool.go:199-210`). Unlike the Messages and Responses decoders, Chat Completions also did not stamp `Message.Source`, leaving generated history without API provenance. These are source-level risks to verify with wire cases, not claims about a live provider. Existing tests already cover one split tool call with trailing usage, an interrupted partial call, and an in-stream error (`completions_test.go:99-145, 320-344`; `stream_error_test.go:18-55`). The root pair test's `cases(t)` is also reused by many unrelated contracts in `providers/`; extending it wholesale would substantially widen this change.

## Lessons and evidence limits

The most valuable combination is pi's explicit API-versus-provider split and Dashi's existing prepared-request evidence. pi's assembler correlates a tool fragment by optional index, then ID (`packages/ai/src/api/openai-completions.ts:495-534`), and its live cross-provider handoff test (`packages/ai/test/cross-provider-handoff.test.ts:1-35`) tests real model acceptance. Dashi can borrow the correlation lesson without inheriting pi's large `OpenAICompletionsCompat` flag surface (`packages/ai/src/types.ts:753-832`). Start with **specific, named fixture cases** and normalized outcomes. A compatibility knob should be introduced only when a fixture proves it is needed, scoped to the relevant route or model, documented with what breaks without it, and visible in `Prepare` evidence. Tests must check what users care about: a tool call is correlated, a malformed partial never executes, a model switch either preserves meaning or explains its rejection, and usage/stop/error facts agree between streaming and blocking. A local fixture proves parser and encoder behavior against recorded bytes; only an item 5 live probe can establish current provider acceptance.

For the first implementation slice, use synthesized, reviewed Chat Completions bytes labeled as such: interleaved two-tool fragments with late metadata; an omitted index resolved only by an existing matching ID; an indexless/ID-less fragment rejected even with one active call; explicit zero kept distinct from omission; conflicting reuse of an index or ID; empty/malformed arguments; and usage after finish. Duplicate IDs and finished invalid arguments need blocking and streaming cases because both can corrupt saved history. Compare a valid blocking body to its equivalent stream. Then pass the resulting completed tool exchange to Anthropic Messages and OpenAI Responses through `Prepare` and check the frozen request body. Leave the separate Gemini module and a full all-route matrix for later. This keeps the evidence honest and the failure names useful to an adapter maintainer.

The matrix is source review, not a live probe. Nvoken has unrelated uncommitted work in `generator.go`; this review cites only clean Nvoken files. Eino's separate provider repository was outside the requested checkout, so its provider status remains unknown. A failed text search alone was not used to label any implementation absent. The current Dashi baseline passes `go test ./providers ./providers/openai/completions` and Gemini's separate-module `go test .`; neither command exercises the proposed cases.
