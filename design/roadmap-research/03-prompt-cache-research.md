## Dashi baseline

`llm.Settings` has no cache request field (`llm/llm.go:360-389`). `llm.Usage` reports disjoint uncached input, cache creation, and cache reads (`llm/usage.go:31-64`), and pricing has one cache-write rate (`llm/pricing.go:24-31`). Anthropic's current Messages request builder does not write `cache_control` (`providers/anthropic/messages/messages.go:151-221`). The model-catalog decision explicitly prices all Anthropic writes at the 5-minute rate until a 1-hour usage bucket and rate land together (`design/model-catalog.md:113-128`). Provider-returned cached tokens can still arise without Dashi requesting them. `Prepare` makes a recordable request and `CapabilityStrict` rejects unknown support (`llm/model.go:91-166`); cache policy should follow that contract. `Runner` constructs one system string and conditionally appends reminder and final-answer instructions (`runner.go:1000-1009,1521-1548`), so marking the end of that whole string would cause avoidable prefix misses when those conditions change. `RequestSnapshot.Input` retains original settings (`llm/request.go:11-35`), and Turn records its Agent (`turn.go:249`); raw affinity placed in settings would be durable even if only its hash goes over the wire.

## Lessons for Dashi

1. **A stable key solves a real host problem.** Two production hosts independently hash conversation identity because they recreate Dive agents. A Dashi caller needs one documented place to supply affinity without disclosing raw IDs. A matching key only routes a request; hits still require an identical prompt prefix.
2. **Good defaults beat manual markers for the common case.** Dive, pi, and OpenHands place stable-system and moving-tail breakpoints in adapters. Dashi must keep Runner's conditional system additions after the stable prefix, or use another minimal boundary; its current single system string does not guarantee this. Test later turns, tool changes, and recovery for byte-stable prefixes.
3. **“Long retention” is not portable.** It means 1 hour for Anthropic and 24 hours on an OpenAI route in pi. Dashi should express an exact requested duration or a provider-specific option, and report effective settings in `Prepare`; never promise a shared duration from a vague enum.
4. **Accounting is part of control.** Anthropic 1-hour writes cost differently. Exposing 1-hour TTL before a separate measured bucket, rate, and budget reservation would make Dashi's cost limits misleading. Cache hits are never guaranteed; diagnostics should compare reads and writes without treating a miss as a failure.
5. **Avoid a cache manager.** Gemini's named cached-content resource has creation, expiry, and cleanup semantics unlike prefix caching. A portable request policy should not pretend to own that lifecycle. Cache warming adds background paid calls and can wait for a real Dashi consumer.

## Evidence limits

This is source inspection at the pinned commits, not a live provider qualification. Negative findings were scoped to the stated packages and request builders; SDK escape hatches or external services can add behavior. The supplied `tmp/research/comparison/` survey was orientation; entries above were checked against checkout source. Provider TTLs, limits, and prices require fresh official-provider verification before implementation and live qualification before claiming hit behavior.
